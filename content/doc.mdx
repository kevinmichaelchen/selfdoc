# A document that edits itself

This page is rendered from `content/doc.mdx`, but you never have to open that
file. Click **✏️ Edit** in the corner, then click any paragraph, heading, or
list — it becomes editable right here. When you click away, your edit is
converted back to markdown and spliced into the source file at the exact
character range this block came from.

## How the trick works

The markdown compiler already knows where every block lives in the source file,
down to the character. A tiny plugin stamps that range onto each rendered
element as `data-edit-start` and `data-edit-end`.

1. You click a block; it becomes `contentEditable`.
2. On blur, the edited HTML is converted back to markdown.
3. The dev server splices it into the file at the stamped range.
4. The page reloads with fresh offsets.

<Note>
  Insertion is the same splice with an empty range: adding a paragraph at
  offset 500 is just "replace characters 500–500".
</Note>

In edit mode, hovering a block also reveals a small toolbar: **+ ¶** inserts a
new paragraph after it, **+ note** inserts a margin note, and **✕** deletes the
block — components included.

<Callout title="The important boundary">
  Prose is editable in the page. Structure — components like this callout, the
  stat row above, their props — is edited in the MDX file, where structure
  belongs. The text *inside* a callout is still prose, so this sentence is
  click-to-edit too.
</Callout>

## What survives a round trip

Inline formatting comes back intact: **bold**, *italics*,
[links](https://mdxjs.com), and `inline code` all convert cleanly in both
directions.[^turndown] Citations survive too: this sentence carries a
footnote,[^footnotes] and editing the paragraph won't corrupt it.

<Note>
  Anything you break, `git diff` will show you — the file is the only state
  there is.
</Note>

> The best interface for editing a document is the document.

## The reading chrome

The table of contents, the per-section reading times, and the progress ring in
the bottom-left corner are all *derived* from the rendered document after it
mounts. Nothing is stored, so none of it can ever disagree with the source
file — or interfere with editing it.

Comments are different: they're reader-state, not document-state. Hit **💬
Comment**, click a block, and leave a note — or a one-tap reaction (😕 lost
me, 📝 needs margin note, 👏 kudos) and an overall grade for the doc.
Feedback works at every zoom level: select a phrase first and the annotation
narrows to exactly those words (highlighted amber), click a heading to
comment on its section, or use the **whole doc** button for global notes. In
comment mode a sidebar lists everything you've left, in document order —
click an entry to jump to it. The **⧉ json** button there exports the lot,
each annotation paired with the text it targets, ready to feed to an agent.
All of it lives in your browser's localStorage, so it works even in the
exported single-file HTML.

**🌡 Heat** is a third lens: it flags blocks that read hot — too long, run-on
sentences, dense vocabulary, em-dash pileups, filler words. Hover a
highlighted block to see why. Like the TOC, it's derived on demand and stored
nowhere.

The ✍ stamp in the topbar is the document's watermark: sessions and distinct
days, active time (idle tabs accrue nothing — there has to be real input),
editing time, edits landed, words added and removed, and the ratio of typed
to pasted characters. Time alone is easy to fake and pasting is easy to hide;
this records both, separately, and stores the tally beside the source in
`content/provenance/` — so care, or the lack of it, leaves a paper trail that
accrues across drafts and ships with the doc.

Next to the stamp, **⧉ copy md** puts the document's raw markdown source on
your clipboard — for feeding the whole post to an agent, or quoting it
faithfully somewhere else.

<Note>
  Comments anchor to a hash of the block's text. Edit everything around a
  block and its comments stay put; rewrite the block itself and they're
  orphaned. That's the honest trade for keeping them out of the file.
</Note>

## Why not just use a CMS

Because the whole point is that there is nothing else: no database, no admin
panel, no sync. The `.mdx` file stays reviewable in a PR, greppable, and
versioned — and the rendered page is simply the nicest editor for it. When you
want to share, `pnpm export` produces one self-contained HTML file with the
reading chrome and comments included, editing excluded.

[^turndown]: The HTML→markdown direction is handled by
    [turndown](https://github.com/mixmark-io/turndown), with a custom rule so
    citation references like this one round-trip as `[^id]` instead of
    flattening into broken links.

[^footnotes]: Citations are standard markdown footnotes (via remark-gfm),
    rendered as endnotes down here. The endnotes section itself is file-edited
    by design — HTML→markdown has no footnote syntax to round-trip through.
